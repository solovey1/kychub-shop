# FarmHub Shop: дизайн

Дата: 2026-11-21. Статус: на согласовании.

## 1. Зачем и для кого

Telegram-магазин цифровых товаров и услуг. Большинство товаров выдаются не из готового склада,
а исполняются людьми: например, регистрация аккаунта Steam под конкретную страну. Поэтому магазин —
это одновременно витрина для покупателя, биржа заказов для исполнителей и рабочее место
для поддержки и админов.

Роли:
- **Покупатель** — работает в чате с ботом, при желании в Mini App.
- **Исполнитель** — выполняет заказы по своим допускам «сервис + страна». Работает в Mini App.
  Получает процент от заказа и чаевые.
- **Менеджер поддержки** — отвечает на тикеты. Работает в Mini App.
- **Админ / владелец** — управляет всем. Работает в Mini App, частично в боте.

Один человек может иметь несколько ролей.

## 2. Цели, не-цели, анти-цели

Цели:
- Каталог с категориями любой вложенности, поиск через поле ввода (inline-режим).
- У каждого товара своя анкета (вопросы покупателю) и свой способ выдачи.
- Система исполнителей: допуски по сервису и стране, очередь и автоназначение, сроки, рейтинг,
  выплаты с холдом, чаевые, анонимная переписка с покупателем.
- Поддержка: тикеты с закреплением за первым взявшим менеджером, полная история.
- Баланс в USDT, отображение в $. Пополнение через платёжные модули, которые пришлёт заказчик.
- Максимально полная админка.
- Языки: русский, английский, украинский.

Не-цели (сейчас):
- Мультивалютность.
- Автоматическое подтверждение выполнения заказа (пока вручную, позже добавим логику).
- Telegram-виджеты (Bot API 10.4): сырые, почти без документации. Вернёмся позже.
- Что делать с оценками покупателей (бонусы, штрафы) — «потом придумаем». Сейчас только собираем.

Анти-цели (провал, даже если работает):
- Вид «вайбкода»: эмодзи в каждой строке, шаблонные тексты, стена кнопок.
- Исполнитель видит чужие заказы, базу клиентов, контакты покупателей или балансы.
- Деньги теряются или задваиваются (двойное зачисление платежа, двойная выдача, гонка при взятии заказа).
- Переписка или результат заказа пропадают.

## 3. Ограничения

- База — текущий репозиторий (шаблон wakaree): Clean Architecture, цепочка
  `Handler → Flow → Interactor → Presenter → View → Renderer`, dishka, FastAPI, PostgreSQL,
  SQLAlchemy 2 + Alembic, Redis, Fluent (aiogram-i18n). Новое пишем в тех же слоях и стиле.
- aiogram обновляем до 3.33 (Bot API 10.4). 3.29.0/3.29.1 отозваны. В 3.33 ломающие изменения:
  фильтры не могут возвращать awaitable, `dp.update.filter` теперь применяется, pydantic ≥ 2.8.
  Python остаётся 3.12.
- Кастомные эмодзи в сообщениях и кнопках работают только если у владельца бота Telegram Premium.
  Сейчас ставим обычные эмодзи, сдержанно. Все тексты и эмодзи только в `.ftl`, чтобы потом заменить
  пак в одном месте.
- Mini App с 20.07.2026 по умолчанию привязан к своему домену (Bot API 10.2).

## 4. Подходы (выбор сделан)

Вопрос: как дать каждому товару свою логику выдачи и свои вопросы покупателю.

- **A. Только данные в БД.** Анкета и тип выдачи настраиваются в админке. Без программиста, но
  нестандартное (внешний API, сложные проверки) не сделать.
- **B. Python-модуль на каждый товар.** Гибко, но каждый товар требует разработчика.
- **C. Гибрид — выбран.** Анкета хранится в БД как данные. Способ выдачи — обработчик из реестра в коде,
  его выбирают в админке и заполняют настройки (JSON). Для особого товара пишется новый обработчик.

Почему C: большинство товаров закрываются готовыми обработчиками, особые случаи — одним классом
без переделки остального. Ни один из изученных open-source магазинов так не умеет (все используют
жёсткий `if/else` по типу).

Также решено:
- Назначение исполнителя: оба режима (очередь «кто первый взял» и автоназначение), режим выбирается
  на уровне сервиса.
- Админка и рабочие места — Mini App (React + Vite + TypeScript). Бот — основной интерфейс покупателя.

## 5. Решения заказчика

- Валюта только USDT, показываем в $.
- Исполнителю платим процент от заказа. Есть холд выплаты (N дней).
- Исполнитель и покупатель общаются анонимно через бота, писать может любая сторона.
- Срок выполнения задаётся на каждый сервис.
- Цена зависит от страны.
- Исполнитель ставит статус «Готово», подтверждение пока делается вручную.
- Рейтинг исполнителя считаем сами по выполненным заказам.
- Покупатель может дать исполнителю чаевые.
- Покупатель видит своих исполнителей: кто сколько заказов ему сделал.
- Покупатель оценивает выполненный заказ. Запрос оценки приходит отдельным сообщением
  по расписанию через некоторое время после выполнения.
- Языки: ru, en, uk.

## 6. Модель данных (основное)

Деньги — `Numeric(18, 2)`, USD. Время — UTC.

Каталог:
- `Category(id, parent_id → Category, title_i18n jsonb, position, is_active)` — дерево (adjacency list).
- `Service(id, code, title, deadline_minutes, assign_mode: queue|auto, executor_percent, is_active)`.
  Например Steam.
- `Country(code ISO-3166, title_i18n)`.
- `Product(id, category_id, service_id?, title_i18n, description_i18n, input_schema jsonb,
  fulfillment_type str, fulfillment_config jsonb, is_active, position)`.
- `ProductVariant(id, product_id, country_code?, title_i18n?, price, is_active)` — цена по стране.
  У товара без стран один вариант.
- `StockUnit(id, variant_id, payload text, is_unlimited, sold_order_id?)` — для товаров со склада
  (ключи, готовые аккаунты). Бессрочная единица (`is_unlimited`) выдаётся каждому покупателю.

Анкета `input_schema` — список полей: `key, label_i18n, type (text|email|number|choice|login),
required, regex?, options?`. Ответы сохраняются в `Order.input_data jsonb`.

Заказы:
- `Order(id, user_id, variant_id, snapshot jsonb (название, страна, цена), price, input_data jsonb,
  status, executor_id?, assigned_at?, deadline_at?, ready_at?, completed_at?, result jsonb?)`.
- Статусы: `awaiting_input → paid → in_queue → assigned → ready → completed`, плюс `failed`,
  `refunded`, `cancelled`. Для выдачи со склада: `paid → completed` сразу.
- `OrderEvent(order_id, actor_id?, type, payload jsonb, created_at)` — история заказа и журнал
  для разбирательств.

Деньги (журнал операций, баланс = сумма записей; у каждой записи остаток после):
- `LedgerEntry(id, user_id, account: main|executor_hold|executor_available, amount, kind
  (topup|purchase|refund|executor_earning|hold_release|tip|withdrawal|admin_adjust),
  order_id?, ref?, balance_after, created_at)`.
- `Payment(id, user_id, provider, external_id, amount, status, raw jsonb)` с
  `unique(provider, external_id)` — защита от двойного зачисления.
- `Withdrawal(id, executor_id, amount, address, status: pending|approved|paid|rejected,
  processed_by?)`.
- Изменение баланса — в транзакции с `SELECT … FOR UPDATE` строки пользователя.

Исполнители:
- `ExecutorProfile(user_id, alias, is_active, percent_override?, max_parallel_orders)`.
  `alias` — анонимное имя для покупателя.
- `ExecutorPermission(executor_id, service_id, country_code)`.
- Рейтинг считается запросом и кешируется в Redis: выполнено, доля успешных, просрочки, отказы,
  среднее время, средняя оценка покупателей.

Оценки и чаевые:
- `OrderReview(order_id, user_id, executor_id, score 1..5, comment?)`.
- Чаевые — `LedgerEntry kind=tip` (списание у покупателя, зачисление исполнителю в холд).

Поддержка и переписка:
- `Ticket(id, user_id, order_id?, manager_id?, status: open|taken|closed, created_at, taken_at, closed_at)`.
- `Conversation` — единая модель для тикета и для чата по заказу:
  `Conversation(id, kind: ticket|order, ticket_id?, order_id?, user_topic_thread_id?)`.
- `Message(id, conversation_id, sender_id, sender_role, text?, media jsonb?, tg_message_id?, created_at)`.

Роли и права:
- `User.roles` — битовая маска: `admin, manager, executor, owner`, плюс тонкие права админа
  (каталог, финансы, пользователи, рассылки). Правило: нельзя выдать право, которого нет у себя.
- `AuditLog(actor_id, action, target, payload jsonb, created_at)` — все действия в админке.

Прочее: `PromoCode` (скидка или бонус на баланс, см. §15a), `PromoCodeUsage`, `Broadcast`, `Setting(key, value jsonb)` (тексты меню, ссылки,
включение/выключение покупок и пополнений), `PaymentGateway(code, is_enabled, settings jsonb)`.

## 7. Выдача заказа: обработчики

Интерфейс (в `application`):
```python
class FulfillmentHandler(Protocol):
    code: ClassVar[str]
    def validate_config(self, config: dict) -> None: ...
    async def on_paid(self, order: Order) -> None: ...   # что делать после оплаты
```
Реестр `dict[str, FulfillmentHandler]`, обработчики собираются через dishka.

Готовые обработчики:
- `stock` — выдать единицу со склада варианта, сразу `completed`.
- `fixed` — одно значение (ссылка, файл) всем покупателям.
- `executor` — отправить в очередь или автоназначение (см. §8).
- `manual` — заказ ждёт админа (для редких товаров без исполнителей).
- Особый товар — новый класс с новым `code`.

Выдача результата покупателю: сообщение бота, данные с кнопкой «Скопировать» (`copy_text`), длинные
данные — файлом `.txt`.

## 8. Исполнители и поток заказа

1. Покупатель выбирает товар → вариант (страну) → заполняет анкету → подтверждает → списание
   с баланса → `paid`.
2. Обработчик `executor` переводит заказ в `in_queue`.
   - Режим `queue`: уведомление всем активным исполнителям с допуском (сервис, страна) и
     свободным лимитом. Кнопка «Взять». Взятие атомарно:
     `UPDATE orders SET executor_id=… WHERE id=… AND executor_id IS NULL`. Остальным уведомление
     меняется на «Заказ взят».
   - Режим `auto`: выбрать подходящего исполнителя с наименьшей нагрузкой, при равенстве — с лучшим
     рейтингом. Исполнитель может отказаться за X минут, тогда назначается следующий.
3. `assigned`: исполнитель видит в Mini App только свой заказ и анкету. `deadline_at = now + service.deadline_minutes`.
4. Переписка покупатель ↔ исполнитель: анонимно, через бота. Покупатель видит псевдоним исполнителя.
   Исполнитель — номер заказа, без имени, username и id покупателя.
5. Исполнитель вводит результат по схеме и ставит «Готово» → `ready`.
6. Админ/менеджер вручную подтверждает → `completed`, результат уходит покупателю. Или отклоняет →
   обратно исполнителю с комментарием.
7. Начисление: `price × percent` в `executor_hold`. Через `hold_days` планировщик переносит сумму
   в `executor_available`. Вывод — заявкой, админ подтверждает.
8. Просрочка: если `deadline_at` прошёл до `ready`, заказ снимается с исполнителя (`in_queue` или
   следующий в auto), просрочка идёт в рейтинг.
9. Через N часов после `completed` покупателю приходит запрос оценки 1–5 и предложение чаевых.
10. Отказ или невозможность выполнить → `failed` → возврат на баланс покупателя (`refund`).

Покупатель в профиле видит «Мои исполнители»: псевдоним, сколько заказов выполнил.

## 9. Поддержка

- Покупатель нажимает «Поддержка» в меню или «Связаться с поддержкой» в заказе (тикет привязан
  к заказу). Пишет в чате с ботом. Если в личке включены темы, тикет получает отдельную тему.
- Новый тикет: всем менеджерам уведомление с кнопкой «Взять» и ссылкой на Mini App. Первый взявший
  закрепляется (атомарный `UPDATE`), остальным уведомление меняется на «Взял <менеджер>».
- Дальнейшие сообщения покупателя уведомляют только закреплённого менеджера.
- Менеджер переписывается в Mini App (чат со всей историей), ответы уходят покупателю от имени бота.
- Админ может передать тикет другому менеджеру и видит все тикеты.
- Хранится всё: текст, медиа (file_id), время, автор.

## 10. Бот (покупатель)

- Главное меню: Каталог, Поиск, Мои заказы, Баланс, Поддержка, Профиль, язык.
- Каталог — навигация по категориям кнопками, пагинация. Поиск — `switch_inline_query_current_chat`:
  покупатель печатает, видит список товаров, выбирает.
- Кнопки: `style=success` для «Купить / Оплатить», `danger` для отмены, `disabled` для недоступного.
- Анкета — пошаговый FSM с проверкой каждого поля, `force_reply`, кнопки для полей типа `choice`.
- Одно «живое» сообщение для навигации (редактирование, а не новые сообщения), как уже делает `Renderer`.

## 11. Mini App

Одно SPA (React + Vite + TypeScript), разделы по ролям. Бэкенд — существующий FastAPI:
- Авторизация через `initData` (проверка подписи), сессия по токену.
- REST для данных, WebSocket для чатов и живых обновлений очереди.
- Разделы:
  - **Покупатель:** заказы, баланс, мои исполнители, чат внутри заказа (с исполнителем и поддержкой).
    Покупка — только в боте.
  - **Исполнитель:** очередь (только допущенные заказы), мои заказы, чат по заказу, ввод результата,
    рейтинг, баланс (холд/доступно), заявки на вывод.
  - **Менеджер:** тикеты (новые/мои), чат.
  - **Админ:** каталог (дерево категорий, товары, варианты, анкеты, способ выдачи), склад (массовая
    загрузка), сервисы и страны, заказы (все, фильтры, ручное подтверждение, возврат, переназначение),
    исполнители (допуски, процент, лимиты, рейтинг), выплаты, пользователи (баланс, блок, роли),
    тикеты, промокоды, рассылки, статистика, настройки, платёжные шлюзы, журнал действий.

## 15. Решения разработчика по итогам проверки

Помечены как решения разработчика; заказчик может поправить.

- **Маршрутизация сообщений покупателя** (согласовано: «максимально просто, лишнее отбрасывать»).
  Правила по порядку, первое сработавшее выигрывает:
  1. Идёт анкета (FSM) — сообщение уходит в анкету.
  2. Ответ (reply) на пересланное ботом сообщение — в ту переписку, откуда оно пришло.
     Связь `tg_message_id → conversation_id` хранится в `Message`.
  3. Сообщение в теме лички — в переписку этой темы. `thread_id` хранится у любой `Conversation`.
  4. Открыта «текущая» переписка (кнопка «Написать» в заказе или тикете, хранится в Redis с TTL
     30 минут) — в неё.
  5. Иначе сообщение отбрасывается. Бот один раз коротко подсказывает, как написать по заказу
     или в поддержку.
- **Результат исполнителя.** У товара есть `result_schema` в том же формате, что `input_schema`.
  По умолчанию: текст + файлы. Админ редактирует схему в карточке товара.
- **Видимость анкеты.** Поле анкеты имеет флаг `hidden_from_executor`. По умолчанию исполнитель
  видит поля, нужные для работы. Username, имя и id покупателя он не видит никогда.
- **Процент исполнителя** считается от фактически оплаченной суммы (после скидки).
- **Платежи до получения модулей.** Делаем тестовый шлюз и ручное пополнение баланса админом,
  чтобы проверять покупки целиком раньше фазы 4.

## 15a. Решения заказчика по итогам проверки

- **Отказы и отмены.** Исполнитель отказался после взятия — заказ обратно в очередь, отказ идёт
  в рейтинг. Покупатель отменяет только пока заказ не взят, возврат полный. Статус `failed`
  с возвратом ставят только админ и менеджер.
- **Возврат и холд.** Пока деньги исполнителя в холде, возврат покупателю отменяет начисление
  исполнителю (`LedgerEntry` с обратным знаком в `executor_hold`). После холда начисление
  окончательное, баланс исполнителя в минус не уходит, возврат идёт за счёт магазина.
- **Исполнителей регистрирует только админ** по Telegram ID. Если пользователя ещё нет в базе,
  создаётся запись с ролью, она подхватывается при первом `/start`. Сами исполнители
  зарегистрироваться не могут.
- **Промокоды** двух видов: скидка на покупку (процент или сумма) и бонус на баланс.
  Ограничения как в `bybit_software_bot`: лимит использований, срок, товар, минимальная сумма,
  только новые пользователи, белый список Telegram ID, многоразовый.
- **Mini App покупателя:** просмотр заказов и баланса плюс чат внутри заказа (с исполнителем
  и с поддержкой). Покупка — в боте.

## 15b. Платежи и выплаты

Платёжный слой переносим из `bybit_software_bot` и переписываем под стиль текущего проекта:
- Порт `PaymentGateway` с методами `create_payment(amount, payment_id, description)` и
  `get_payment_info(payment_id, amount)`. Реестр шлюзов по коду.
- Шлюзы: CryptoBot (Crypto Pay), Binance Pay, NOWPayments.
- Модель опроса, без вебхуков: раз в минуту опрашиваем неоплаченные счета младше 24 часов.
  Статусы двигаются только вперёд. Раз в 3 минуты добиваем оплаченные, но не зачисленные.
  Зачисление идемпотентно (`unique(provider, external_id)`).
- Токены шлюзов — только в `.env` или в зашифрованных настройках, не в коде.

**Сейчас (решение заказчика от 2026-11-21):** исполнитель сам указывает свой кошелёк для выплат
(`ExecutorProfile.payout_wallet`) и нажимает «Вывести». Кнопка пока заглушка: создаёт заявку
`Withdrawal(pending)` на адрес кошелька, списывает `executor_available` и уведомляет админа.
Реальная отправка денег — позже, по варианту ниже или другому.

Отложенный вариант автоматических выплат:
- У исполнителя два счёта: `executor_hold` и `executor_available`. Вывести можно только доступное.
- Выплата — через Crypto Pay `transfer`: USDT уходит исполнителю на кошелёк в @CryptoBot
  по его Telegram ID, мгновенно, без адресов и сетей. Исполнитель должен хотя бы раз запустить
  @CryptoBot. `spend_id = withdrawal.id` защищает от двойной отправки.
- Заявка до порога `auto_payout_limit` проводится автоматически. Выше порога — после подтверждения
  админом. Минимальная сумма вывода и порог задаются в настройках.
- Запасной вариант — ручная выплата: админ переводит сам и отмечает «выплачено».
- На кошельке приложения Crypto Pay должны лежать средства для выплат. Админка показывает этот
  баланс и предупреждает, когда его не хватает.
